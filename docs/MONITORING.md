# 오류 로그와 운영 알림

## 구현 범위

- 안전한 로그: 이벤트명, 서버 생성 requestId, 허용된 오류 분류/코드/HTTP 상태만 기록합니다. 원문, 표시 이름, 비밀번호, 토큰, SQL, params, stack, message, cause 전체를 기록하지 않습니다.
- 보호 API의 인증과 핸들러는 같은 요청 ID를 사용합니다. 오류 응답의 requestId와 X-Request-Id, 사용자 화면의 문의 ID로 로그를 찾습니다.
- 인증 실패는 계속 401, 인증 서비스 장애는 503입니다. 인증·Origin·계정별 접근 검사는 유지합니다.
- GET /api/health는 DB 또는 AI 장애 시 503입니다. 기존 database/ollama 필드를 유지하며, ollama는 선택한 AI 제공자의 상태입니다.
- Health는 로그인 보호를 유지합니다. 익명 감시의 401을 서비스 장애로 오인하지 마세요. 인증된 감시 계정의 토큰 만료·갱신도 관리해야 합니다.

## 운영 설정 안내 (아직 미설정·미검증)

1. Vercel 프로젝트의 로그 접근자를 최소화하고 보존 기간을 정합니다. 사용 가능한 알림 기능/요금제 또는 외부 로그 수집 도구를 확인합니다.
2. 수신 채널(이메일/Slack 등)을 정한 다음 5xx 급증, auth_unavailable/password_auth_unavailable, health_database_failed, health_ai_failed 이벤트를 대상으로 알림을 연결합니다.
3. 예상된 잘못된 비밀번호/401/단발 429는 긴급 호출에서 제외하고, 지속 발생만 별도로 집계합니다. 같은 장애는 묶어서 알리고 복구 알림도 설정합니다.
4. 실제 입력/계정정보/키를 알림 본문에 포함하지 않습니다. 이벤트명과 문의 ID만 전달합니다.
5. 개발 환경에서 의도한 인증·DB·AI 실패를 한 번씩 만들어 로그와 응답의 ID가 일치하는지, 알림 도착과 복구 알림까지 확인합니다. 운영 자격증명을 변경해 장애를 만들지 마세요.

코드 로그만으로 자동 알림이 발송되지는 않습니다. 이번 변경에는 외부 전송 SDK·웹훅·수신 채널 및 클라이언트 오류 수집이 포함되지 않았습니다. 테스트·빌드·실제 알림 발송 검증은 사용자 실행으로 남겨두었습니다.

## 사용자 실행

```bash
pnpm test:run
pnpm lint
pnpm build
```

diagnostics/api-error/health 테스트와 기존 인증 회귀 테스트를 확인하고, 로그인된 브라우저에서 Health 장애 표시·문의 ID가 표시되는 오류를 확인하세요.
