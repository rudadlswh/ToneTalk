# 스터디 포인트

퀴즈 첫 선택 정답 20 XP, 정답 공개 없이 퍼즐 완성 25 XP, 롤플레이 4회 대화 완료 35 XP를 **계정·학습 유형별 하루 한 번** 저장한다. 한국 시간 기준 하루 최대 80 XP다. 퀴즈/퍼즐은 기존과 같이 지급 조건을 처음 충족한 문제에서 지급하며, 5문제 전체 완료를 요구하지 않는다. 플래시카드·오답 복습은 추가 XP가 없다. 기존 원장과 총액은 소급 차감하지 않는다.

## 데이터 흐름과 지급 규칙

**5단계부터 모든 신규 지급은 서버 근거를 검증한다.** 오늘의 AI 문제와 내 저장 문장은 `PUT /api/study/daily`에서 DB 문제로 채점하고 답안과 XP를 같은 트랜잭션으로 저장한다. 롤플레이는 서버 발급 세션의 4회 응답을 확인하고 진행과 XP를 같은 트랜잭션으로 저장한다. [STUDY-REWARD-PROOF.md](STUDY-REWARD-PROOF.md)의 API·적용 절차를 따른다.

`POST /api/study/points`는 기존 원장의 정확히 같은 요청을 확인하는 용도로만 남긴다. 신규 직접 지급은 409/POINTS_PROOF_REQUIRED로 거절한다. 과거 브라우저 미저장 큐의 증빙 없는 요청은 삭제하지 않고 보관·안내하며 뒤에 있는 기존 적립 확인을 막지 않는다. 이미 지급된 XP는 회수하지 않는다. 서버가 확인한 누적 XP만 표시한다.

- 모든 유형: `(owner_id, activity, credited_on)` 고유 인덱스로 **유형별 하루 1회**를 보장한다. `credited_on`은 DB 트랜잭션 시작 시각의 `Asia/Seoul` 날짜이며 브라우저 시계·문제 세트 날짜를 신뢰하지 않는다. 오늘의 AI 문제/내 저장 문장은 같은 한도를 공유하고, 새 대화·다른 상황·언어로 바꿔도 chat 한도는 같다.
- 기존 `(계정, 유형, 문제 ID, 세트 날짜)` 중복 제약과 답안/대화 완료 상태도 유지한다. 날짜가 바뀌어도 이미 완료된 문제·같은 대화의 재시도에는 새 XP를 주지 않는다. 다음 날의 새로운 유효한 완료에는 다시 지급할 수 있다.
- 한도 충돌은 `ON CONFLICT DO NOTHING`으로 정상 처리한다. 풀이 결과·대화 완료는 저장하고 응답의 `points`는 0이다. 그 밖의 DB 오류는 원래처럼 완료 상태와 XP를 함께 롤백한다.
- eventId는 요청 재시도 키다. 자정을 넘긴 재시도도 같은 eventId를 유지한다. INSERT 후 응답 유실/합계 조회 실패가 발생해도 재시도에 추가 지급되지 않는다.
- 원장이 합계의 유일한 원본이다. 별도 잔액 컬럼을 두지 않으므로 적립 기록과 잔액을 이중으로 갱신하지 않는다.
- 로그인 계정만 읽고 쓸 수 있다. private 스키마, RLS 활성화, PUBLIC/anon/authenticated 테이블 접근 회수를 유지한다. 직접 SQL을 쓰는 서버가 항상 owner 조건을 적용한다.

## API / 프로필

### 과거 미저장 포인트 복구 (1단계 도입 기록)

아래는 이전 브라우저 큐의 보관·재전송 방식이다. **5단계의 새 화면은 큐에 신규 적립을 만들지 않는다.** 남아 있는 기존 요청 중 실제 원장 행이 확인되는 요청만 완료 처리하며, 나머지는 자동 지급 대신 경고와 함께 보관한다.

- 스터디에서 최초 요청을 전송하기 **전** localStorage의 `tonetalk:study-points:v1:{인증 사용자 UUID}:{eventId}`에 적립 입력과 발생일을 보관한다. 세션 토큰·비밀번호·대화 원문은 보관하지 않는다. 문제 ID에는 생성 문장의 일부가 포함될 수 있으므로 공유 기기에서는 브라우저 데이터 관리에 주의한다.
- 같은 브라우저·사이트 주소에서 같은 계정으로 스터디 재진입, 브라우저 online/focus 이벤트, 수동 재시도 시 미저장 요청을 복구한다. 다른 기기·브라우저·배포 주소에는 브라우저 미저장 큐가 공유되지 않는다. 프로필만 열거나 브라우저가 닫힌 동안의 백그라운드 재시도는 하지 않는다. 추가 서비스나 의존성은 없다.
- 서버가 검증한 사용자 UUID를 SessionBoundary에서 전달한다. 재전송 전 `/api/auth/session`을 확인하고 매 요청의 `x-tonetalk-account`도 검증된 사용자와 비교한다. 이 헤더는 소유권 지정이 아니라 **동일 계정 확인용**이다. 쿠키가 중간에 바뀌어도 불일치 시 403/ACCOUNT_CHANGED로 적립·조회 모두 차단한다. 헤더 없는 기존 클라이언트는 기존 인증 방식과 호환된다.
- 계정이 바뀌거나 로그아웃해도 다른 계정의 요청을 전송하거나 삭제하지 않는다. 같은 계정으로 돌아오면 다시 저장한다. 계정 변경 시 클라이언트 상태도 새로 마운트한다.
- 요청 하나당 저장 키 하나를 써 여러 탭이 다른 요청을 덮어쓰지 않는다. 같은 요청이 여러 탭에서 재전송되면 기존 DB의 중복 제약을 사용한다. 성공 확인 시 해당 계정·eventId 키만 삭제한다.
- 재전송은 순차 처리한다. 네트워크 실패, 401/403/500, 잘못된 성공 응답에는 기록을 유지한다. 429는 Retry-After 동안 재전송하지 않고 이후 사용자 재시도/재진입/online/focus로 재개한다. 무한 재시도 타이머는 두지 않는다.
- 저장 공간 부족·localStorage 차단·손상된 기록은 경고한다. 이때 자동 복구를 약속하지 않으며 현재 화면에서 수동 저장을 완료하도록 안내한다. 브라우저 사이트 데이터 삭제·비공개 창 종료·브라우저 자체 저장소 제거 후에는 복구할 수 없다. 손상된 기록을 자동 삭제하지 않는다.
- 1단계에서는 최초 도착일로 지급했지만, 5단계에서는 원장 없는 큐 요청에 새 지급일을 부여하지 않는다. 이미 커밋된 eventId의 재확인은 자정을 넘겨도 추가 지급하지 않는다.

`POST /api/study/points`: `{eventId: UUID, activity: quiz|puzzle|chat, activityId: string}`. 최대 2 KB/ID 240자, 알 수 없는 필드 거절. 기존 기록 확인 응답 `{awarded:false, points:0, totalPoints, requestId}`. 기록 없으면 409/POINTS_PROOF_REQUIRED. 잘못된 요청 400, 인증 필요 401, 출처 오류 403, 본문 초과 413, 빈번한 요청 429, DB 오류 500.

`GET /api/study/points?cursor=...`: `{totalPoints, items:[{id,activity,points,createdAt}], nextCursor, requestId}`. 20건씩 최신순 `(created_at,id)` 커서 페이지네이션. 다른 계정의 커서도 해당 계정 데이터에는 접근하지 못한다. 타임스탬프는 밀리초 정밀도로 커서 직렬화 시 오차를 없앤다. 모든 응답은 private/no-store.

프로필의 포인트 섹션은 기본 프로필/서비스 상태 조회와 독립적으로 로드한다. 누적 XP, 학습 유형, 적립량, 한국 시간 적립 시각과 이전 기록 더 보기를 제공한다. 빈 기록과 DB 조회 오류를 구분한다.

## 적용 / 검증 / 롤백

### 유형별 일일 제한 (2026-09-16)

추가 SQL: `supabase/migrations/20260916033055_study_daily_reward_limit.sql`. `study_point_events`가 있는 환경에 적용한다. 새 패키지/테이블/API/환경 변수는 없다.

1. 기존 행에 기본값 없이 nullable `credited_on` 날짜 컬럼을 추가한다.
2. 기존 실제 적립 시각을 한국 날짜로 변환하고 계정·유형·날짜별 첫 행 하나만 일일 적립 표시를 채운다. 나머지 옛 행은 NULL로 남겨 **기록·금액·합계·ID를 전부 보존**한다. 이미 오늘 받은 XP도 바로 제한에 포함된다.
3. 새 행의 기본값을 DB의 한국 날짜로 지정하고 unique index를 만든다. NULL은 과거 중복 기록 보존을 위한 호환 값이며 앱 지급 경로는 날짜를 직접 지정하거나 NULL로 보내지 않는다. private 서버 전용 접근 통제를 유지한다.

SQL 전체를 한 트랜잭션으로 적용한다. 컬럼 변경의 테이블 잠금이 backfill/인덱스 생성까지 유지되어 지급 요청이 끼어들지 못한다. 재실행은 기존 일일 표시와 기록을 변경하지 않는다. 운영은 백업/복구 계획 확인 후 짧은 점검 구간에 대상 배열을 `['tonetalk_prod']`로 제한하여 적용하고 UI를 배포한다. 단순 앱 롤백으로 이 DB 제한은 해제되지 않으며 원장을 지우는 롤백은 하지 않는다.

개발 `tonetalk_dev`에만 적용했다. 운영에는 3~6단계의 미적용 SQL과 이 변경을 검토·적용한 뒤 배포해야 한다. 빈 환경은 현재 bootstrap이 같은 컬럼·기본값·인덱스를 포함한다.

회귀 검증은 동시 다른 문제/AI·저장 세트/새 채팅, 유형별·계정별 격리, 다음 지급일, 완료 재시도, 기존 다중 적립 보존·한국 자정 backfill·재실행, DB의 직접 중복 INSERT 거절, 지급 실패 롤백, 화면의 0 XP/응답 유실 안내를 포함한다. 실제 DB 테스트는 임시 fixture만 정리하고 실제 Auth 계정은 생성/삭제하지 않는다.

## 보안 범위

XP는 개인 학습 기록이며 현금·상품·랭킹 보상이 아니다. 5단계부터 서버 문제/채점·응답 완료 근거 없이 임의 ID로 직접 적립할 수 없다. 다만 학습 화면에 정답 데이터가 있으므로 이를 읽는 자동 풀이, 의미 없는 대화를 반복하는 행위까지 막지는 않는다. 과거 지급 기록의 학습 근거를 소급 검증하지도 않는다. 경제적 보상이나 공개 순위 도입 전에는 별도의 시험·자동화 방지 정책이 필요하다.

2026-09-14 Supabase Advisor: 새 원장의 [RLS Enabled No Policy](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) INFO는 브라우저 직접 접근을 전부 막는 서버 전용 설계에서 의도한 상태다. 별도로 [유출 비밀번호 보호 비활성화](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) WARN이 있다. Auth 설정은 이 작업에서 변경하지 않았다.
